# PDF差分検出アルゴリズム 技術仕様書

## 目標

- 真陽性率(検出率): 100%（見逃しゼロ）
- 偽陽性率(誤検出率): 10%以下
- 処理時間: 60ページで2分以内（要求定義書では1分以内だが、技術的制約により2分以内で進める）
- 対象: テキストベースPDFのみ（画像ベースPDF除外）

## 評価指標

- 真陽性率(検出率)、真陰性率、偽陽性率(誤検出率)、偽陰性率(見逃し率)
- 処理時間、読み順序精度
- 詳細は別途評価指標資料を参照

## 既存アルゴリズムのテストからの判明点と変更

### テキストベースPDF対応
- 画像ベースPDFではなく、テキストベースPDFのみに対応でよい
- OCR処理を省略し、PyMuPDFによる直接テキスト抽出で高速化
- フォント情報、位置情報の活用が可能

### 完全一致ベース採用
- 類似度では「令和5年度」「令和6年度」のようなものを見逃すため、完全一致ベースがよい
- difflib.SequenceMatcherによる厳密な文字列比較
- 類似度閾値による判定を廃止し、tag != 'equal'での判定

### 検出単位の検討
- 完全一致アルゴリズムにより1文字単位の検出を行っている（要求定義書準拠）
- 現状: 単語ベース実装済み
- 課題: 意味単位（「令和6年10月23日」）が分割される問題
- 課題: アノテーションの定義の難しさ（どこまでを一つの意味単位とするか）
- 提案: 意味単位認識による適応的単位設定（表示・評価用）

## ベースライン構築結果からの課題

### 位置情報ソートの限界
- 位置情報を用いてmeiji-document-checkの3.2ピクセル閾値ソートで人が読む順番に変更しても、以下の問題が発生
  - 斜め文字: 文章が斜めを向いている場合の座標処理困難
  - フォントサイズ差: 大きなフォントと小さなフォントの行判定誤り
  - 複雑レイアウト: 表構造、カラムレイアウトでの順序混乱

### 表記揺れによる過剰検出
- 全角半角の違い（「１２３」vs「123」）
- 空白文字の差異（全角空白 vs 半角空白）
- 句読点の有無（「こんにちは。」vs「こんにちは」）

## 提案アプローチ

### 1. 人間が読む順番に並び替える

#### 読み順序推定アプローチ（画期的手法）

**正解データ作成**
- 人間が読む順番のアノテーション（文章単位のみ）
- 複雑レイアウト（表、カラム、図表）を含む多様なサンプル準備

#### 入力情報統合

**Azure AI Document Intelligence情報**
- セクション認識、表構造、レイアウト分析
- 読み順序の推定結果
- 段落・見出しの階層情報

**PyMuPDF空間情報**
- 座標情報（x, y, width, height）
- フォント情報（サイズ、種類）

**画像情報**
- 画像領域の座標
- テキスト領域との重複関係

#### 画期的アルゴリズム: LLM中心型読み順序推定

**ステップ1: 入力データ統合**
- PDFページ画像 + レイアウト構造情報 + テキスト座標情報を1つのプロンプトに統合
- 例: 「この文書の文章を人間が読む順序で並び替えてください」
- アノテーション済みサンプルを参考例として提示

**ステップ2: LLM推論実行**
- 文書知識の活用: 「第1条→第2条」「上記の通り→下記参照」等のパターン認識
- 視覚的理解: PDFページ画像から表・カラム・図表の配置を理解
- 論理的推論: 文脈のつながりを考慮した読み順序決定

**ステップ3: 品質チェックと改善**
- 自己評価: LLMが推定結果の自然さを数値評価（1-10点）
- 低品質判定時: 代替案を自動生成して再評価
- 最適解選択: 最も自然な読み順序を最終出力

**ステップ4: 長文書対応**
- ページ単位処理: 各ページを個別に読み順序推定
- 文脈継承: 前ページの読み順序パターンを次ページに活用
- 階層処理: ページ全体→段落→文章→単語の順で段階的に処理

### Azure AI Document Intelligence コスト概算

**開発期間（4週間）**
- 処理想定: 1日200-60ページ（試行錯誤・テスト含む）×20営業日 = 4,000-10,000ページ
- 料金: $10/1,000ページ（レイアウト分析モデル）
- 開発コスト: 約$40-100

**運用期間（月間）** ※要望定義書の利用規模に基づく
- 利用頻度: 1日30回の差分チェック（要望定義書より）
- 想定ページ数: 平均60ページ/回（最大60ページ対応）
- 日間処理: 30回×60ページ = 1,800ページ/日
- 月間処理: 1,800ページ×22営業日 = 39,600ページ
- 料金計算:
  - レイアウト分析モデル: $10/1,000ページ × 39.6 = $396/月
- 月間運用コスト: 約$400
- 年間運用コスト: 約$4,800

#### LLM予測システム（コア技術）

**プロンプト設計**
- 役割設定: 「文書レイアウト解析の専門家として」
- タスク指示: 「人間が読む自然な順序で文章を並び替える」
- 出力形式: JSON形式での順序付きテキスト配列
- 制約条件: 「全文章を含める」「順序の根拠を説明する」

**対話型改善**
- 基本フロー: LLM推定 → 人間確認 → 修正指示 → 再推定
- 学習機能: 修正パターンを記憶して次回に活用
- 動的調整: 文書の複雑さに応じてプロンプトを最適化

**前処理の工夫**
- レイアウト可視化: 文章の位置関係を分かりやすく表現
- 構造認識: 見出し・箇条書き・表などの要素を事前に特定
- 関連度計算: 文章間のつながりを数値化

##### フォールバック戦略
外部API障害・コスト超過・セキュリティ制約時の代替手法:

1. **ローカルLLM手法**
   - Llama2/3、Code Llama等のオンプレミス展開
   - GPU要件: NVIDIA A100 40GB以上推奨
   - 処理速度: 外部APIの2-3倍時間
   - セキュリティ: 完全内部処理

2. **画像処理 + PyMuPDF手法**
   - PDFをページ画像に変換後、OpenCVで領域検出
   - PyMuPDFの座標情報と画像解析の組み合わせ
   - 表・カラム境界の画像認識による読み順序推定
   - 処理速度: 外部APIと同等
   - 精度: 中程度（単純レイアウトで70-80%）

3. **ルールベース手法**
   - 既存の3.2px閾値ソートの拡張
   - フォントサイズ、位置情報による優先度設定
   - 表構造パターンの事前定義
   - 処理速度: 最高速
   - 精度: 低程度（単純レイアウトで60-70%）

### 2. 順番並び替え後の完全一致アルゴリズム

#### 前処理（正規化）
- 文字正規化
  - 全角半角統一（数字、英字、記号）
  - Unicode正規化（NFC形式統一）
  - 空白文字統一（全角空白→半角空白）
- 意味保持正規化
  - 改行文字、タブ文字の統一
  - 連続空白の単一空白化
  - 行末句読点の統一処理

#### 意味単位認識
- パターンベース認識
  - 日付パターン: 「令和X年Y月Z日」「YYYY/MM/DD」
  - 金額パターン: 「金XXX円」「XXX万円」
  - 制度情報: 「第X条」「附則第Y項」
- 結合処理
  - 認識されたパターン内の単語を結合
  - 単一の意味単位として差分検出対象化

#### 差分検出エンジン
- 階層的比較
  1. 意味単位レベル比較
  2. 単語レベル比較（意味単位未認識部分）
  3. 文字レベル比較（詳細差分）
- SequenceMatcher適用
  - 完全一致以外を差分候補として抽出
  - replace, insert, delete の分類
- 後処理フィルタ
  - 除外ルール適用（表記揺れパターン）

## リスク要因

### 技術的リスク
- LLM API の応答速度、コスト制約
- 複雑レイアウトでの読み順序予測精度
- 意味単位認識の漏れ、誤認識

### 外部API関連リスク
- コスト: LLM API利用料金の予算超過リスク
- セキュリティ: 機密文書の外部API送信に伴う情報漏洩リスク
- 可用性: 外部API障害時のシステム停止リスク
- 依存性: 特定ベンダーへの技術依存リスク

### 運用リスク
- アノテーション作業の品質、効率
- 文書種類の多様性への対応
- システム負荷、可用性の確保

### ステークホルダーリスク
- 要求仕様の変更: ステークホルダー要望への対応可否
- 期待値管理: 技術的制約と期待値のギャップ
- 承認プロセス: セキュリティ・コンプライアンス承認の遅延
