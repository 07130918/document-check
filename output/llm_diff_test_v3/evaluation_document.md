# 文書差分検出アルゴリズム評価ドキュメント

## 1. 概要

本ドキュメントは、LLMを活用した文書差分検出アルゴリズムの技術仕様と評価方法をまとめたものです。ベースラインアルゴリズムとの比較を通じて、LLM活用による精度向上を定量的・定性的に評価します。

## 2. アルゴリズムの技術仕様

### 2.1 ベースラインアルゴリズム

#### 処理フロー
1. **文書抽出**: PyMuPDFを使用してPDFから単語単位のBounding Box情報を直接抽出
2. **読み順序推定**: 物理的な位置（Y座標優先、次にX座標）に基づく機械的な順序推定
3. **差分検出**: テキストの完全一致/部分一致（類似度0.9以上）による単純なマッチング
4. **差分分類**: 削除・追加・変更・レイアウト変更（50ポイント以上の移動）

#### 特徴
- 高速処理（外部API不要）
- 位置ベースの単純な読み順序推定
- テキストマッチングによる基本的な差分検出

### 2.2 LLM活用アルゴリズム

#### 処理フロー

1. **Azure Document Intelligenceによる文書抽出**
   - 入力: PDF/Word/PowerPointファイル
   - 出力: 階層的な文書構造（単語→行→段落）
   - データ形式:
     ```
     {
       "content": "抽出されたテキスト",
       "polygon": [x1,y1,x2,y2,x3,y3,x4,y4],  // 8つの座標値
       "page": ページ番号
     }
     ```

2. **日本語文字のグループ化**
   - Azure出力の文字レベルデータを意味的な単語に結合
   - ひらがな・カタカナ・漢字の連続を1つの単語として処理
   - 英数字・記号は個別に処理

3. **LLMによる読み順序推定**
   - 入力データ形式（見開き2ページ単位）:
     ```
     [
       {
         "index": 0,
         "text": "テキスト内容",
         "x": X座標,
         "y": Y座標,
         "width": 幅,
         "height": 高さ
       },
       ...
     ]
     ```
   - LLMプロンプト:
     ```
     あなたは文書の読み順序を推定する専門家です。
     以下の文書要素の読み順序を推定してください。

     [見開きページの場合の特別な指示]
     1. 左ページから右ページへの自然な読み順序を考慮
     2. 各ページ内では上から下、左から右の順序を基本
     3. 見開き全体でのコンテンツの流れを重視

     要素リスト: [上記JSON形式のデータ]

     人間にとって自然な読み順序でインデックス番号のリストを返してください。
     ```
   - 出力: 読み順序のインデックスリスト

4. **差分検出処理**
   - difflibを使用したシーケンスマッチング
   - 置換操作の詳細分析（1対1、多対多の置換を識別）
   - 各差分に前後3単語の文脈情報を付加

5. **LLMによる文書解析**
   - 文書構造解析プロンプト:
     ```
     以下の文書の構造を解析してください。
     [文書全文]

     以下の項目を含むJSON形式で回答してください：
     {
       "document_type": "文書タイプ",
       "sections": ["主要なセクション名のリスト"],
       "key_elements": ["重要な要素"],
       "summary": "文書の簡潔な要約"
     }
     ```

6. **位置スコア計算による差分検出**
   v3アルゴリズムでの位置類似度計算:
   - X座標とY座標の差からユークリッド距離を計算
   - 距離を正規化して0-1の類似度スコアに変換
   - 総合スコア = テキスト類似度 × 0.95 + 位置類似度 × 0.05

## 3. 評価項目と方法

### 3.1 定量評価項目

| 評価項目 | 説明 | ベースライン実績 | LLM活用実績 | 目標値 |
|---------|-----|-----------------|------------|--------|
| 総差分数 | 2024年文書で検出された差分の総数 | 134件※1 | 122件※2 | - |
| 適合率（Precision） | 検出した差分のうち、正しかった割合 | 38.8% | 42.6% | 90% |
| 偽発見率（誤検出率） | 検出した差分のうち、間違えていた割合 | 61.2% | 57.4% | 10% |
| 真陽性率（正解率） | 実際の差分のうち、正しく検出できた割合 | 94.5% | 94.5% | 100% |
| 偽陰性率（見逃し率） | 実際の差分を見逃した割合 | 5.45% | 5.45% | 0% |
| 処理時間 | 文書ペアの処理にかかる時間 | 4.17秒 | 78.56秒 | 300秒(ファイルサイズにかかわらず) |

※1 ベースライン：バウンディングボックス数（文字が連続している部分は1個とカウント）
※2 LLMアルゴリズム：個別のバウンディングボックス数

## 4. 目視評価手順

1. **両アルゴリズムの出力比較**
   - 同一文書ペアに対する両アルゴリズムの差分検出結果を比較
   - 差分数を記録

2. **差分の妥当性評価**
   - 各差分について、以下の観点で評価：
     - 人間が見て明らかに差分と認識できるか
     - 差分の範囲（開始・終了位置）が正確か

3. **エッジケースの確認**
   - レイアウト変更への対応
   - 複数行にまたがる変更の検出
   - 表やリストの変更検出
   - 画像周辺のテキスト変更

4. **LLM固有機能の評価**
   - 読み順序の自然さ
   - 文書構造解析の正確性
   - 変更要約の適切性
   - リスク評価の妥当性

### 4.3 評価基準

#### 正しい検出と判定する場合
- 人間が見て明らかに差分と認識できる変更
- 意味的に重要な変更（日付、金額、名称等）
- レイアウト上の大きな変更

#### 誤検出と判定する場合
- 改行位置の違いによる変更

## 5. アルゴリズム比較分析

### 5.1 処理性能比較

| 項目 | ベースライン | LLM活用 | 比較 |
|------|------------|---------|------|
| 処理速度 | 高速（ローカル処理） | 低速（API呼び出し） | ベースラインが優位 |
| コスト | 低（計算資源のみ） | 高（Azure + OpenAI API） | ベースラインが優位 |
| スケーラビリティ | 高 | API制限あり | ベースラインが優位 |

### 5.2 技術的特徴の比較

| 項目 | ベースライン | LLM活用 | 比較 |
|------|------------|---------|------|
| OCR技術 | PyMuPDF（基本的） | Azure Document Intelligence（高精度） | LLM活用が優位 |
| 日本語処理 | 文字単位の処理 | 意味的な単語単位の処理 | LLM活用が優位 |
| 差分検出粒度 | 単語単位（連続文字を1つとカウント） | 個別バウンディングボックス単位 | 同等 |

### 5.3 検出できなかった差分の分析

両アルゴリズムで共通して検出できなかった差分（偽陰性率5.45%分）：
- 画像内のテキスト変更
- 目次の変更

### 5.4 特記事項

#### ベースラインアルゴリズム
- 良かった点：
  - 差分検出の粒度が単語単位
  - レイアウト変更のない簡単な差分を検出できる
- 改善が必要な点：
  - レイアウト変更や大幅な変更がある場合，誤検出などが多くなる

#### LLM活用アルゴリズム
- 良かった点：
  - ベースラインと比べて誤検出が少ない
- 改善が必要な点：
  - フォントサイズ等の変化にも反応してしまい，誤検出を引き起こす
  - レイアウト変更や大幅な変更がある場合，誤検出や見逃しが多くなる
